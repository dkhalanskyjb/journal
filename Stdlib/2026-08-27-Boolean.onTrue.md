Boolean.onTrue
==============

Implementation
--------------

```kotlin

@IgnorableReturnValue
inline fun Boolean.onTrue(action: () -> Unit): Boolean =
    if (this) {
        action()
        true
    } else {
        false
    }

@IgnorableReturnValue
inline fun Boolean.onFalse(action: () -> Unit): Boolean =
    if (this) {
        true
    } else {
        action()
        false
    }

```

Analysis
--------

### Usage forms

Boolean values are typically returned as function results and checked in
`if`/`when` expressions.

`onTrue` shines on the producer side:

```kotlin
// Before:
fun query(): Boolean = if (queryImpl()) {
    register()
    true
} else {
    false
}

// After:
fun query(): Boolean = queryImpl().onTrue { register() }
```

It may hurt readability when the return value isn't exactly the input `Boolean`:

```kotlin
// Before
run {
    val queryResult = query()
    if (queryResult) {
        doSomething()
    }
    return !queryResult
}
// or
run {
    if (query()) {
        doSomething()
        false
    } else {
        true
    }
}

// After
run {
    !query.onTrue { doSomething }
}
// or
run {
    query.onTrue { doSomething }.let { !it }
}
// or
run {
    (!query).onFalse { doSomething } // double negation
}
```

On the consumer side where the only outcome of checking a Boolean is conditional
execution of some code, `onTrue` is okay, too, but not an actual improvement:

```kotlin
// Before
if (query()) {
    doSomething()
}

// After
query().onTrue {
    doSomething()
}
```

On the other hand, if the `Boolean` is consumed by more complex constructs than
a mere `if`, `onTrue` is actively harmful:

```kotlin
// Before
run {
    val queryResult = query()
    if (queryResult) {
        doSomething()
    }
    if (queryResult && anotherCondition) {
        return constantValue
    }
}

// After
run {
    if (query.onTrue { doSomething() } && anotherCondition) {
        return constantValue
    }
}
```

This resembles the limitations of other Kotlin functions, like `let`,
`apply`, and `with`, which can be nested in complex, unreadable ways due to the
lack of experience.

### Prior art

#### Kotlin

There are several with a similar form, available on `Result`-like classes:

```kotlin
@IgnorableReturnValue
inline fun <T> Result<T>.onSuccess(
    action: (value: T) -> Unit
): Result<T>

@IgnorableReturnValue
inline fun <T> Result<T>.onFailure(
    action: (exception: Throwable) -> Unit
): Result<T>

@IgnorableReturnValue
inline fun <T> ChannelResult<T>.onSuccess(
    action: (value: T) -> Unit
): ChannelResult<T>

@IgnorableReturnValue
inline fun <T> ChannelResult<T>.onFailure(
    action: (exception: Throwable?) -> Unit
): ChannelResult<T>

@IgnorableReturnValue
inline fun <T> ChannelResult<T>.onClosed(
    action: (exception: Throwable?) -> Unit
): ChannelResult<T>
```

`fun <T> T.onNonNull(action: (T) -> Unit): T` is not explicitly defined, but
is available as `t?.also { action(it) }`.

#### Rust

Somewhat surprisingly, Rust *didn't* adopt a similar function:
see <https://doc.rust-lang.org/std/primitive.bool.html#implementations>.
This is in contrast with its

* <https://doc.rust-lang.org/std/option/enum.Option.html#method.inspect>
  (equivalent to `value?.apply { f() }` or, in some contexts,
  `Result<*>.onSuccess`).
  Note the lack of `inspect_none`.
* <https://doc.rust-lang.org/std/result/enum.Result.html#method.inspect>
  and
  <https://doc.rust-lang.org/std/result/enum.Result.html#method.inspect_err>
  (direct equivalents to `Result<*>.onSuccess` and `Result<*>.onFailure`)

However, the monadic nature of `Option` permits an orthogonal solution to this:
<https://internals.rust-lang.org/t/inspection-for-booleans/21240/5>

Kotlin can't adopt that approach, as the idiomatic equivalent doesn't look
natural, even if we assume `action()` can't return `null`:

```kotlin
fun query(): Boolean = queryImpl().ifOrNull { action() } != null
```

### Edit Distance on Changes

#### No longer execute anything

```kotlin
if (b) {     | b.onTrue {
    action() |   action()
    true     | }
} else {     |
    false    |
}            |
--------------------------
           b
```

`onTrue` wins.

#### Execute `action` unconditionally (the Bool is pure)

```kotlin
if (b) {     | b.onTrue {
    action() |   action()
    true     | }
} else {     |
    false    |
}            |
--------------------------
       action(); b
```

`onTrue` wins. `if (b)` leads to two possible false starts:

1) Repeating the `action` in both branches:

```kotlin
if (b) {
    action()
    true
} else {
    action()
    false
}
```

2) (Caught by IDEA) Moving the `action()` out without simplifying:

```kotlin
action()
if (b) {
    true
} else {
    false
}
```

#### Execute `action` unconditionally (the Bool is effectful)

```kotlin
if (query()) { | query().onTrue {
    action()   |   action()
    true       | }
} else {       |
    false      |
}              |
---------------------------------
    query().also { action() }
```

`onTrue` wins if the programmer has the presence of mind to recognize
`also` as the combination of `onTrue`/`onFalse`.

#### Execute something else on `false`, too

```kotlin
if (b) {      | b.onTrue {
    actionT() |   actionT()
    true      | }
} else {      |
    false     |
}             |
---------------------------
if (b) {      | b.onTrue {
    actionT() |   actionT()
    true      | }.onFalse {
} else {      |   actionF()
    actionF() | }
    false     |
}             |
---------------------------
    b.also {
        if (it) {
            actionT()
        } else {
            actionF()
        }
    }
```

`onTrue` loses.
The `onTrue {}.onFalse {}` version is attractive, and the transformation from it
into the final `also` form isn't obvious.

Proposal
--------

* Implement and document `onTrue` to be `.also { if (it) { action() } }`.
* Implement an IDEA inspection for collapsing `onTrue { }.onFalse { }` chains
  into one `also` invocation.
* Implement an IDEA inspection for collapsing `onTrue { }.onTrue { }` chains
  into one `onTrue` invocation.
* Generalize the IDEA inspection detecting
  `if (query()) { true } else { false }` to encompass
  `if (query()) { actionT(); true } else { actionF(); false }`.
  Provide `onTrue`/`onFalse`/`also` replacements for all scenarios.

Open questions
--------------

### Naming

#### onTrue

Gemini:

> In strict English grammar, onTrue is a bit "icky" because "on" is a
> preposition that normally precedes a noun,
> while "true" is an adjective.
> However, in programming vernacular,
> onTrue is entirely standard and well-understood.

ChatGPT:

> onTrue is grammatically fine.
> It reads as “when/on becoming or being true, perform this action,”
> similar to onSuccess or onEach.

#### onTruth

Gemini:

> onTruth, on the other hand, is definitely not better.
> While "truth" is a noun (fixing the grammatical ick),
> it introduces a semantic ick.
> In programming, we deal with literal true and false values,
> whereas "truth" sounds philosophical, abstract, or implies
> "truthiness" (like in JavaScript),
> which doesn't fit Kotlin's strict typing.

ChatGPT:

> onTruth sounds philosophical and refers to the concept of truth,
> not the Boolean value—so I’d avoid it.

#### ifTrue

Gemini:

> If another developer writes this:
> `val status = isValid.ifTrue { calculateStatus() }`
> They would likely expect status to hold the result of `calculateStatus()`.
> Finding out that status just holds true (the original receiver)
> definitely violates the principle of least astonishment.

ChatGPT:

> ifTrue sounds like a control-flow operation,
> so callers may expect either Unit or a transformed/nullable
> result—not necessarily the original Boolean.

#### alsoWhenTrue/alsoIfTrue (suggested by both LLMs)

Gemini:

> It makes the return type and side-effect behavior 100% transparent.
> A developer sees alsoIfTrue and instantly knows,
> "Ah, this executes a block and returns the boolean
> so I can keep chaining."

ChatGPT:

> Accurately advertises that it returns the original Boolean,
> but feels implementation-driven.
